Design principles

The README's five rules, in short.

1

Everything in Terraform

Helm release versions, ConfigMaps, IAM, alert rules and cleanup tasks are resources. If it cannot be reviewed in a PR and reverted, it does not exist in production.

2

Converge ephemeral state

Pod IPs change. Modules query live cluster state and reconcile load balancer targets to match, so each apply is a reconciliation loop.

3

Fail at plan time

Every input has a description. Inputs with a real constraint have a validation block, so a bad environment name is rejected by plan, not by a provider an hour in.

One workflow, many environments

A Terragrunt layer runs the same workflow for dev and prod without copying it. These are the live units found in the repo.







  
Use a module

  
Terraform 1.7 or later. Replace every placeholder with your own values.

  

    


module "log_archive" {
  source = "./AWS/modules/s3_lifecycle"

  bucket_name = "app-logs-prod"
  environment = "prod"
  log_prefix  = "logs/"
}

    

    


terraform fmt -check -recursive
terraform init -backend=false
terraform validate
trivy config .

      
CI runs fmt, validate and a Trivy IaC scan across the modules.

    

  






  

    What this does not do
    
    
      
  • This is a personal portfolio repository. The README says every name, account ID and metric was replaced with generic placeholders.

  • The catalog reads variables and resource types with a pattern scan. It is not a Terraform parser, so a variable declared in an unusual way could be missed.
    • 
      
  • Validating a module is not the same as applying it. Nothing here claims a live deployment.
